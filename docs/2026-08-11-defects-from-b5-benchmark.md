## D-1【高】`_downscale_for_ocr` が `np.array()` の**後**に効く

**現象**：`OCR_MAX_SIDE`（既定 3000）は大画像の瞬時内存峰値を抑えられない。
縮小が走る時点で既に原寸のラスタが内存に載っているため。

**証拠**：`ocr_engine.py:311-316` ——`convert_from_bytes` → PIL Image → `np.array()`（`:314`）
→ その後に `_downscale_for_ocr`（`:316`）。加えて `pdf2image` は `output_folder=None` の時
`communicate()` で未圧縮 PPM を全量親プロセスへ読み込むため（`pdf2image/pdf2image.py:249-265`）、
同一頁のラスタが **PPM／PIL／ndarray の約 3 部**同時に存在する瞬間がある。

**実測での裏取り（B5 ③）**：54 頁档の峰値が 35 頁档より **+580MB** 跳ねた。原因は頁数ではなく
その区間に含まれる **15.4Mpx の頁（p52）**。1–35 頁の最大は 9.4Mpx。
すなわち 内存峰値 ≒ 常駐基線（≒1.1GB）＋ **単頁最大画像**のラスタ化コスト。

**影響**：miniPC（Windows・構成未確認）で A3 級／高 DPI スキャンが 1 枚混ざるだけで OOM に
至り得る。**頁数を制限しても防げない**——決定変数が頁数ではないため。

**修復方向**（実施時に評審で決める）：
1. `convert_from_bytes` に `size=` を渡し、**poppler 側で縮小してから**受け取る
   （PPM 自体が小さくなるので 3 部共存の基数が下がる）
2. `output_folder` を使い一旦ディスクへ落として逐次読む（親プロセスの全量読込を回避）

**注意**：`OCR_MAX_SIDE` の**既定値そのものは変えない**（精度に効く。生産既定の変更は別議）。
直すのは「効くタイミング」であって閾値ではない。

**回帰の歯型**：大画像を含む単頁 PDF を食わせ、修復前後で
`benchmark_memory.run_sampled` の峰値が有意に下がることを実測で示す。採取器と口径（プロセス木の
同時刻 RSS 合計）は B5 で既に用意済み。

## D-2【高】pypdf 欠落時に「全ファイルを内存へ」の退避路へ落ちる

**現象**：pypdf が使えないと `_split_pdf_pages` は警告 1 行を print して**空を返す**。
逐頁分岐は return せず末尾段へ落ち、`f.read()` で全ファイルを内存に載せる。さらに
`_ocr_with_paddleocr` が全バイトに対し頁数ぶん `convert_from_bytes` を反復（O(n²) のディスク書込）、
strategy C は全 PDF を inline data として Gemini へ送出する。

**証拠**：`ocr_engine.py:425-427`（空 return）／`:2135-2137`（逐頁分岐が return しない）／
`:2295-2296`（末尾段 `f.read()`）／`:1911`→`:409`／`:304-311`

**影響**：**現行 UI 生産で到達可能**。headless 未上線なので「legacy」ではない（この点は Codex も
複審で明示的に認めた）。依存欠落という稀な条件だが、落ち方が最悪（内存・ディスク・API 課金の三重）。

**修復方向**：`_split_pdf_pages` が空を返したら**起動を拒否する**か、少なくとも末尾段へ落とさず
明示的に失敗させる。黙って重い経路へ滑り込ませない。

**B5 側の暫定措置（実施済）**：`benchmark_preflight.assert_pypdf_available()` が測定前に落とす。
ただしこれは benchmark を守るだけで、生産経路は無防備のまま。

## D-3【中】opencv が 2 つ入っている（開発機）

**現象**：`opencv-python-headless 5.0.0.93` と `opencv-contrib-python 4.10.0.84` が同居。
どちらの `cv2` が読まれるかは import 順・インストール順に依存し、再現性を損なう。

**証拠**：`pip list`（2026-08-11・venv311 実測）。`requirements.txt:40-43` は OCR スタックの版を
固定していない（`paddleocr>=3.0` / `paddlepaddle>=3.0`）。

**影響**：測定結果の可搬性。miniPC 側の構成が不明なため、そもそも同じ物を測っているかを保証できない。

**修復方向**：どちらか一方に寄せ、`requirements.txt` で版を固定する。
**依存変更は趙の許可事項**（全局 §1）なので実施前に申請する。

## 控制面倉側（本倉の範囲外・上申のみ）

- **`SDV_POST_UNKNOWN_MAX_REENTRY` が死配置**：`config.py:51` で定義後 `src/` `tests/` に消費者なし。
  真値は `reconciler.py:38` のハードコード 3 で、`runner.py:266-271` は `max_reentry` を渡していない。
  **契約 §9-1 の当該項を回填しても生産挙動は変わらない**。
- **`max_handoff_move_retry`** も同様にハードコード 3（`reconciler.py:40`）だが §9-1 の 5 件に含まれず、
  5 件だけ回填すると漏れる。
- **起動閘門** `max_attempts >= breaker_failure_threshold`（`config.py:126-146`）——この 2 つは
  **対で動かす**必要がある。
