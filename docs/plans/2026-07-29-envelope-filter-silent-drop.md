# 封筒フィルタによる無音頁欠落の修正（IP-401）

作成日: 2026-07-29
**対象ブランチ: `main`（本番）** — sandevistan 側へは実装後に同期（ユーザー裁定）
起票理由: 顧客（社長夫人）フィードバック ③「54枚アップしたが仕訳は53件」

---

## 1. 事実（再現済み・証拠あり）

### 1.1 欠落した票

`舞鶴パーク` 駐車場 現金 200円 領収証（1ページ、161×213pt の小型サーマル）。

### 1.2 PaddleOCR の実出力（venv311 で実測）

```
'舞鶴パーク\n☆领収证☆\nNo.05\n入庫26/07/1723：33:2\n精算26/07/1801：10:1\n現金\n200円'
conf = 0.883
```

「領**収**証」→「领**収**证」と誤認識（繁簡混在）。

### 1.3 判定結果

```
clean_text len          = 55        (閾値 60 未満)
has_receipt_structure   = False     (_receipt_structure に不一致)
_is_envelope_page       = True
```

`ocr_engine.py:1853`（main）で `continue` → **yield されず、Sheets にも占位行にも一切残らない**。

### 1.4 Gemini は動いていた

`_route_ocr_strategy` は封筒判定より**前**にあり、Strategy C で
PaddleOCR テキスト＋原画像を Gemini に送信済み。`page_raw_data` が Gemini の戻り値。

顧客の `MF_Import_Data`（IDO）を実読して確認：

- 領収書タブの取引No は 1〜53 で終わり、舞鶴パークの行は**無い**
- 赤系「認識不能ページ」占位行も**無い**

Gemini と Vision 兜底が両方空なら占位行が書かれるはずで、それが無い以上
`page_raw_data` は非空だった。つまり **Gemini は読めていたが、PaddleOCR の
誤認識テキストだけを見た `_is_envelope_page` が単独で棄却した**。

### 1.5 根本欠陥

```python
def _is_envelope_page(ocr_text, raw_data):   # raw_data を受け取るが
    ...                                      # 関数本体(636-677)で一度も参照しない
    text_lower = ocr_text.replace(" ", "")    # PaddleOCR テキストのみで裁決
```

Strategy C（交差検証）の設計意図が、この一点で単一エンジンの拒否権に潰されている。

## 2. 目標 / 非目標

### 目標

1. Gemini が有効な仕訳を構成できたページは、OCR テキストが何であれ**棄却されない**
2. 除外されたページが**無音で消えない**（監査タブで可視化）
3. PaddleOCR の異体字・繁簡誤認識で構造キーワードが失配しない
4. 整形段階の例外で**残りの全ページが巻き添えで消えない**（Codex 指摘、新規追加）
5. ④ 社会保険料通知書がアップロードされても**誤った仕訳を作らない**（2026-07-30 追加、§3.8）

### 非目標

- 封筒判定そのものの廃止（本物の封筒/送付状の除外は引き続き必要）
- ⑤ 会社別勘定科目カスタマイズ（顧客のルール確定待ち、別 Plan）
- ① GAS バックアップ（コード修正ではなく Apps Script 設置＋`setupTriggers()` 実行）
- headless / posting_ledger 関連（**`main` に存在しない**。sandevistan 同期時に別途検討）

## 3. 設計（Codex 評審を反映した確定版）

### 3.1 封筒判定を「前置拒否権」から「事後説明器」へ

```
現行:  OCR → Gemini → [封筒判定] → 棄却(無音) or 正常処理
                        ↑ OCR テキストのみで Gemini の成果を否決できる

改後:  OCR → Gemini → entries 構築
                        ├─ entries あり → 採用（記帳）
                        │                  └─ 封筒判定が同時に命中 → 監査タブに
                        │                     「分岐」記録（記帳は止めない）
                        └─ entries なし → 封筒判定で理由を分類
                                            ├─ 封筒 → 監査タブに除外記録（MF 区には書かない）
                                            └─ それ以外 → 従来通り「認識不能」占位行（赤・MF 区）
```

**目標1 が構造的に達成される。** Gemini が仕訳を作れた時点で棄却経路が存在しない。

### 3.2 除外ページの留痕先：独立監査タブ（ユーザー裁定）

MF データ区（仕訳タブ）には書かない。`_get_or_create_tab` を再利用し
専用タブ（例: `除外ページ監査`）へ追記する。

列: `日時 / ファイル名 / ページ / 判定 / 理由 / OCR文字数 / 原票URL`

理由:

- MF 区に黄色占位行を混ぜると取引No・行 fingerprint を消費し、MF インポート
  データを汚す（Codex「高」指摘を採用）
- それでも「無音で消える」のは不可、顧客は数を数えるしか発見手段がない
- 監査タブなら MF 区は綺麗なまま、追跡は可能

**機械可読フィールドで制御する**（Codex「中」採用）:
result dict に `_excluded_page: True` / `_exclude_reason: "envelope"` を持たせ、
`main.process_file` がそれを見て監査タブへ振り分ける。memo 文言でのパースはしない。

`_excluded_page` の頁は `error_pages` に数えず、`count` には数える
（`count == error_pages` による Failed→無限リトライを回避）。

### 3.3 整形段階の例外境界（Codex「厳重」採用）

現行 `main` の逐頁ループは `try` が `_route_ocr_strategy` と Vision 兜底までしか
覆っておらず、`_yield_page_results` の消費は `try` の**外**にある。整形段階を
判定より後ろへ動かすと、畸形 Gemini JSON の例外が最外層まで飛び、**PDF の
残り全ページが無音で消える**——元の不具合より重大な退行になる。

対応: `_yield_page_results` の消費を逐頁 `try/except` の内側に入れ、例外時は
`_page_error` + `_error_class` を立てた result を yield して次ページへ進む。

### 3.4 異体字・繁簡の正規化（Codex「中」を反映して縮小）

単方向・比較専用の変換表を使う（`↔` の双方向置換は禁止）。

```
NFKC 正規化 → 単方向写像: 领→領, 证→証, 收→収, 请→請, 买→買, 计→計
```

**構造キーワードと財務キーワードの両方**を同一の `normalized_text` に対して
照合する（Codex 指摘の一貫性欠如を修正）。封筒/送付状/挨拶状キーワード側にも
同じ正規化を適用し、分類器全体で一貫させる。

**位置づけの訂正**（Codex「中」採用）: §3.1 導入後、正規化はもはや「票の消失を
防ぐ」機能ではない。「entries が作れなかったページ」を監査タブ行きにするか
赤い認識不能行にするかの**分類精度**を上げるだけの hardening である。
本 Plan では実施するが、中核修正ではない。

### 3.5 適用範囲は広げない（Codex「高」採用）

判定は**PDF 逐頁ループのみ**に留め、単頁PDF/画像の尾段へは広げない。
`_yield_page_results` は両経路が共用するため、封筒判定は
「逐頁ループから渡されたときだけ有効」になるようフラグで制御する。
単頁画像への適用可否は実データ収集後に別途判断する。

### 3.8 社会保険料通知書の除外（④、2026-07-30 追加）

**事実**: 顧客の表に実在する誤り（IDO、2026/07/29 14:46 書込、両行とも黄系）:

| 取引No | 取引日 | 科目 | 金額 | 摘要 |
|---|---|---|---|---|
| 1 | 2026/07/21 | 保険料 | 319,000 | 6月分保険料納入告知 |
| 2 | 2026/06/30 | 保険料 | 319,000 | 5月分保険料領収済 |

「保険料納入告知額・領収済額通知書」は券面に当月の**納入告知額**と前月の
**領収済額**の2口が印字されており、両方を仕訳化していた。

**社員からの共通ルール宣言（2026-07-30、最優先）**:
「社会保険料に関する会計処理はアップロードせずに口座振替資料として処理すると
共通ルールとして統一しています」

したがって顧客が当初述べた「当月分のみ反映」は**採らない**。口座振替側で
既に記帳される以上、SS 側が当月分を1行作れば銀行側と二重計上になる。

**確定挙動（ユーザー裁定 2026-07-30）: 零仕訳＋提示行。**

- 検出したら仕訳を一切生成しない
- MF タブ（監査タブではない）に占位行を1行書き、摘要に
  `⚠ 社会保険料通知書です。口座振替資料として処理してください（仕訳は作成していません）`
- MF タブに書く理由: これは正常な除外ではなく**運用ルール違反の通知**であり、
  顧客が必ず目にする場所でなければ意味がない（封筒の監査タブ行きとは性質が違う）

**検出方法**: 日本年金機構の定型書式なので OCR テキストのキーワードで足りる。
`保険料納入告知額` / `領収済額通知書` / `日本年金機構` 等を §3.4 の
`normalized_text` 上で照合する。

**設計上の位置づけ**: ③ の `_excluded_page` 機構をそのまま再利用し、
`_exclude_reason="social_insurance_notice"` で分岐する。書込先だけが
封筒（監査タブ）と異なる。新機構は作らない。

**「掃かない前提に賭けない」（ユーザー裁定 2026-07-30）**: 顧客が
「井戸会計では今後スキャンしない」と述べても、コードはそれに依存しない。
RENTAL・将来の新規顧客を含め**全プロファイルで常時有効**にする。

### 3.6 閾値 60 は据え置き

§3.1 により本件は閾値に触れずに解決する。コメントの「正式な領収書は必ず構造
キーワードを持つ」という断定は本事故が反証したので、best-effort 分類器である
旨に書き換える（Codex「低」採用）。

## 4. タスク一覧（DoD 付き）

### T0. 例外境界の修正（Codex 厳重・最優先）

- 実装: 逐頁 `try` を `_yield_page_results` 消費まで拡張
- **DoD:** 整形段階で例外を投げる fixture で、当該頁のみ `_page_error=True` に
  なり後続ページが正常に yield される単体テスト
- ~~**DoD:**（R4）その result の `_error_class` が期待値であることも断言する~~
  → **実施時に事実訂正（2026-07-30、第3輪）**: `main` 分支に `_error_class` /
  `_classify_page_error` は**存在しない**（`grep -n "_error_class\|classify"
  ocr_engine.py main.py sheets_output.py` → 0 hit）。消費側 `main.py:347` は
  `_page_error` のみで分岐する。R4 は §8 の厳重1・厳重2・中5 と同根で、Codex が
  sandevistan 作業ツリーを読んだことに起因する。よって断言対象を
  `_page_error` ＋ 例外型名を含む `memo` に置換。`_error_class` の導入は
  範囲拡大にあたるため行わない（sandevistan 同期時に再評価）
- **DoD（置換後・達成済み）:** 当該頁の result が `_page_error=True` /
  `_unrecognized=True` / `entries=[]`、`memo` に例外型名を含み、`page_bytes` を
  保持する。後続ページは巻き添えにならず正常 yield される

**実施記録（2026-07-30）**: `ocr_engine.process_pipeline` の逐頁ループで
`_yield_page_results` の消費を `next()` + `try` に置換（`yield` 自体は try の外に

### T2. 監査タブへの書き出し

- **DoD:**（R2）entries 有効＋封筒シグナル命中で、MF タブに正常な仕訳行が

### 3.7 二重書込の失敗語義（R3 への回答）

**原則: 監査タブは可観測性設備であり、帳簿データではない。その失敗が記帳を
阻害してはならない。ただし「唯一の留痕」である場合だけは保底経路へ退避する。**

| ケース | 監査書込失敗時の挙動 |
|---|---|
| entries 有効 + 封筒シグナル（分岐記録） | 警告ログのみ。MF は既に正しく書けており帳簿は正しい。監査は諦める |
| entries 空 + 封筒命中（真の除外） | 監査タブが唯一の留痕。失敗したら **MF 区の赤い「認識不能」占位行へ退避**して必ず可視化する |

書込順序: MF 区を先、監査タブを後（帳簿を人質に取らせない）。

**冪等性について（R3 の再試行懸念への回答）**: `main` 分支では
`_excluded_page` を `error_pages` に数えず `count` には数えるため、除外頁が
1 頁でも存在すれば `count > error_pages` となり `process_file` は Failed 判定に
入らずファイルを歸檔する（`main.py:380`）。歸檔されれば再スキャンされないので、
**監査行が再試行で重複することはない**。逆に `count == error_pages` で保留される
ケースには定義上 `_excluded_page` の頁が 0 件しか存在しえない。よって本分支では
専用の冪等キーは不要。

（注: sandevistan 同期時は `posting_ledger` があるためこの論証は成立しない。
同期時に第1輪の厳重1・厳重2 と併せて再設計すること。）
