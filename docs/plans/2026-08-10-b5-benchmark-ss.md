## 4. 実施設計

### 4.1 ① 単頁 SS データ面コンポーネント耗時

**名称の根拠**：Firestore 往復を fake transport に置換する以上、これは契約が言う整链 E2E ではない。**「端到端 P99」と名乗らない**（評審 #11・複審認可）。契約閾値への回填は U14 就緒後の真整链補測を経てから——それは控制面の活であり本批の阻塞項ではない（§0.4-7）。

**新設ファイル**：`benchmark_e2e.py`（仓根・生産コード無改変）

**入力形状**：契約形状＝**事前に 1 頁／1 切片へ切り出したもの**。切出処理は**計時区間外**。

**実行前提（DoD の一部）**：
- `HEADLESS_MODE=1` を明示設定し `config.headless_mode() is True` を断言（E4）
- 実行後に環境を復元
- 入力が実際に 1 頁であることを検証

**計時**：

| 点 | 位置 | 内容 |
|---|---|---|
| `t0` | `main.process_file(...)` 呼出直前 | — |
| `t1` | 同 返り直後 | 主指標＝`t1 - t0` |
| 分段 | `commit_page` 前後 | 副指標（`post_page` の CONFIRMED は含まない旨を明記） |

- `time.perf_counter` を使う（`golden_replay.freeze_time` が `sheets_output.datetime` を差し替えるため）
- **generator ラッパ・writer デコレータ・頁号突合器は全て廃止**（評審 #15）——`process_file` 1 回＝1 標本なので不要
- **`main.process_pipeline` への monkey-patch はしない**。`main.py:20` は `from ocr_engine import (...)` の局所束縛であり、`ocr_engine` 側を包んでも `main` には効かない（既存テストが全て `patch.object(main, "process_pipeline", ...)` を使っているのはこのため）。そもそも本 Plan では真 pipeline を走らせるので patch 自体が不要

**構成要素**：

| 要素 | 真/偽 | 根拠 |
|---|---|---|
| `process_pipeline`（PaddleOCR＋Gemini） | **真** | 測定対象そのもの |
| `SheetsWriter`（頁原子書込） | **真**（K1 のテスト表宛） | — |
| `PostingLedger` | **真の実装 ＋ fake Firestore transport** | K5 の忠実実装（評審 #11） |
| `PageUrlResolver` | 真（ただし単頁入力では上傳は発生しない＝E3） | — |

**層別報告（成功者バイアス回避・評審 #9）**：各試行はちょうど 1 レコードを産み、耗時・終態・提交有無を持つ。`POSTED` / `EXCLUDED` / `PLACEHOLDER` / `RETRYABLE` / `UNKNOWN` / `ESCALATE` で層別し、**全体分布も併記**。タイムアウトは打切り記録として残し、**黙って除外しない**。

**標本条件（評審 #8・複審認可）**：
- 分位数算法＝**nearest-rank** に固定（事前確定・報告に明記）
- 成功標本が閾値未満なら **P99 とは名乗らず**、P50・max・標本数のみ報告
- 同一環境・同一シナリオごとに別々に算出。cold（初回・モデル冷）と warm を混ぜない
- `_dup` 副本は除外し、票種で層化した重複なし標本リストを作る
- 実行順はランダム化（Sheets 成長・Drive キャッシュの効果が特定標本に偏らないように）
- 各試行で Sheets の前後行数と Drive 操作種別（初回上傳／既存再利用）を記録

**AST 網**：`test_pipeline_consumers.py:180-196` は「`process_pipeline` を呼ぶ仓根の非 `test_` ファイルは文字列 `_excluded_page` を含むこと」を強制する。本スクリプトは `main.process_file` 経由なので**直接は呼ばない**。実装時に AST 判定に掛かるか確認し、掛かるなら除外頁の層別処理（上記）が実体を伴うのでそれで満たす。

### 4.2 ② 票序漂移

**観測不能と判定**（評審 #12）。契約 headless では 1 入力＝1 頁で `page_num` が恒に 1、かつ直列単一プロセスで専用 Sheet に書けば行順は自明に単調。跨 job の「票序」を定義する真値順序・照合キー・漂移距離のいずれも本 harness には存在しない。

**趙の裁定要（§6 R9）**：(a) ② を「現行契約形状では観測不能」と報告して閉じる／(b) 頁内多票の yield 順と落表順の一致確認だけを行う（狭義の観測）／(c) 全局 dispatch sequence と票据安定キーを定義して並行・再試行・重放シナリオまで作る（範囲拡大・非推奨）。

### 4.3 ③ 内存峰値 ＋ PaddleOCR CPU 档耗時

**2 シナリオに分割**（評審 #4／E5）：

| シナリオ | 形状 | 位置づけ |
|---|---|---|
| **S-A（検収用）** | `HEADLESS_MODE` **未定義**＝現行 UI 生産形状。真の `process_pipeline(478 頁 PDF)` を最後まで消費 | **478 頁 OOM 判定はこちら**。pypdf・pdf2image・PaddleOCR・generator 消費方式は全て真。Gemini のみ明示的な seam で固定小応答に差し替え可 |
| **S-B（参考）** | 契約 headless 単頁 | 参考値。478 頁 DoD には参加しない |

**新設ファイル**：`benchmark_memory.py`（親監視プロセス）＋ worker（独立子プロセス）

**採取口径（評審 #5#6#7）**：

| 項目 | 方針 |
|---|---|
| 主指標 | **固定サンプリング周期での「同一時刻に生存するプロセス木の RSS/working-set 合計」の峰値**。両プラットフォーム共通 |
| 禁止 | 各プロセスの**高水位を足し合わせない**（異時刻の峰値を重畳してしまう）。RSS 合計は共有頁の二重計上を含む旨も注記 |
| macOS 付加指標 | `resource.getrusage(RUSAGE_SELF).ru_maxrss`（**単位＝バイト**、本 session 実測確認） |
| Windows 付加指標 | `peak_wset` / `peak_pagefile` / `private`。`peak_pagefile` ≠ システム commit charge である旨を明記。可能なら Job Object／性能カウンタでプロセス木 commit を補う |
| 比較 | **Mac と Windows の数値を直接比較しない**。Mac は本機基線、miniPC は合格判定 |
| cold/steady | `ru_maxrss` 等の高水位はプロセス内でリセット不能なので、**warmup 後に読んでもモデル読込峰値が残る**。よって cold-start と steady-state を**別プロセス**で採る |
| サンプリング周期 | 事前に固定して報告。短命な `pdftoppm` を取りこぼす可能性を明記し、既知量を確保して即終了する子プロセスの結合テストで採取器自体を検証 |
| tracemalloc | 使わない（C++ tensor と子プロセスが見えない） |
| 合格判定 | Mac の峰値との一致ではなく、**worker の終了コード 0・消費頁数 478・OOM/システム終了なし** |

**環境記録（評審 #11・拡張）**：`OCR_MODEL_TIER`／`OCR_MAX_SIDE`／`cpu_threads`／機種・OS・CPU・物理内存／Python 版とアーキ／**Poppler・pdftoppm 版**／両機の `pip list`（paddleocr・paddlepaddle・paddlex・pypdf・numpy・pdf2image・opencv）／**実際に読み込まれた Paddle モデル名とモデルディレクトリのハッシュ**／モデルキャッシュの冷暖／入力のサイズ・DPI・ハッシュ／git SHA。

**server 档は測らない**（§6 R4）。

**pypdf 退避路（評審 #14・複審認可）**：本 benchmark では**前置 fail-fast のみ**——pypdf 不可なら実行を拒否し環境不合格として報告する。**危険 fallback（全ファイル読込＋O(n²) ディスク書込＋全 PDF を Gemini へ）は独立した生産欠陥として別途立項し趙へ上申**する。benchmark の成果物として「危険経路に到達できた」を数えない。**これを legacy 扱いしない**——現行生産は UI 版であり、現在到達可能な経路である。

### 4.4 契約 §9-1 との関係（範囲の収斂・評審 #15）

① から導けるのは **`stall_threshold` への入力 1 件のみ**。残り 4 件——`classify_timeout`（控制面の分類段）／`max_attempts`（連続無進展の輪次上限）／`POST_UNKNOWN` 重入上限／断路器 N・窓・半開——は**単頁耗時の分位数から導出できない**。可靠性・SLO・故障復帰方針の決定であり、控制面の分類 benchmark・故障注入・業務許容度の判断を要する。

**報告にはこの旨を明記し、「数値を埋めた＝完了」としない。**

### 4.5 報告

- 生データ＝**JSONL/CSV**（1 試行 1 行）。Markdown は薄いテンプレートで生成し、**golden 文字列テストは作らない**（評審 #21／#15）
- 落档先：`docs/2026-08-1x-b5-benchmark-report.md`
- 構成：三節（①②③）＋ 環境節 ＋ 未測項節 ＋ 上申節
- **推奨値は出さない**（§6 R5）
- 別途 **validator** を用意し、報告と生データの整合を機械判定する（§5 の検収に使う）

| # | タスク | DoD（述語） |

## 9.7 ③ Mac 基線の実測結果（2026-08-11）——**「頁数ではなく単頁最大画像が効く」**

環境＝`macOS-26.5.2-arm64`／物理内存 36,864MB／14 コア／`git_sha=c23724e`／
採取周期 0.2s／既定値のまま（`OCR_*` 全て未設定＝mobile・MAX_SIDE 3000・cpu_threads 1）。
シナリオ＝S-A（UI 多頁形状・`HEADLESS_MODE` 未設定）。生データ＝`curve.json`／`memory_sa.json`。

| 頁数 | 峰値（プロセス木の同時刻 RSS 合計） | 増分 |
|---|---|---|
| 1 | 1097.2 MB | — |
| 5 | 1220.7 MB | +30.9 MB/頁 |
| 10 | 1220.2 MB | **−0.1 MB/頁** |
| 20 | 1227.1 MB | **+0.7 MB/頁** |
| 35 | 1288.5 MB | +4.1 MB/頁 |
| 54 | 1868.6 MB | **+30.5 MB/頁** |

**線形近似は棄却**（`12.07×頁数+1068.9`、R²=0.79）。よって「478 頁＝6.8GB」等の外挿は
報告に載せない。

**読み取れた三点**

1. **常駐基線 ≒ 1.1GB**——1 頁でも 1097MB。PaddleOCR の 5 モデル（doc_ori／UVDoc／
   textline_ori／v5_mobile_det／v5_mobile_rec）＋Python runtime であり頁数と無関係。
2. **10→20 頁はほぼ横ばい（+0.7MB/頁）**——逐頁流式処理は効いている。当初 Plan §4.3 が
   「真因候補 #1」とした `PdfReader.resolved_objects` の単調累積は、**この区間では観測されない**。
3. **35→54 頁で +580MB の跳躍**——頁数由来ではなく、その区間に**大きな画像の頁**が
   入ったため。実測で裏取り済：1–35 頁の最大画像 9.4Mpx に対し 36–54 頁は **15.4Mpx**（p52）。

**結論：峰値 ≒ 常駐基線 ＋ 単頁最大画像のラスタ化コスト。頁数は決定変数ではない。**
「N 頁で OOM するか」という問い自体が的を外している——1000 頁でも小画像なら安全、
10 頁でも A3 高精細スキャンが混ざれば危ない。趙 2026-08-11 裁定（478 頁は無意味）は
結果的に**より強い形で裏付けられた**。

**連動する既存欠陥（B5 範囲外・上申）**：`_downscale_for_ocr` は `np.array()` の**後**に
効く（`ocr_engine.py:314`→`:316`）ため、`OCR_MAX_SIDE=3000` ではこの瞬時峰値を抑えられない。
大画像は原寸のまま一度内存へ載る。縮小を `np.array` の前へ動かせばリスク源を直接断てるが、
生産コード改変につき本批では触らない（§1.2-4）。

**miniPC 側の測定方案は未定**——`total_memory_mb`／`cpu_count`／依存版／`pdftoppm` 版／
`ocr_env` が不明なまま方案は組めない（趙 2026-08-11 指摘）。`python benchmark_memory.py --env`
の出力待ち。**Mac の絶対値は miniPC へ持ち込めない**（物理内存が天井を決めるため）。
