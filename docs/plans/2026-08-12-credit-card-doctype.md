## 3. アーキテクチャ決定

5 設計線（D1 族分類 / D2 検算元帳 / D3 重複検出 / D4 プロンプト / D5 税区分）を
敵対的レビューにかけ 19 件の P0 を検出、さらに Codex 評審で 15 件の指摘を得た。
線をまたぐ矛盾を以下のとおり裁決する。辯論の記録は附録 B。

### AD-0. 頁の去向は単一の解析関数が決める（多頭裁決の禁止）

族分類・重複判定・builder が各自「この頁をどうするか」を主張すると、
矛盾したときの勝者が実装の書き順で決まってしまう。**優先序を文書で固定する。**

```
resolve_page_disposition(dedup_verdict, entry_count, page_class) -> Disposition

優先序（上から評価、最初に当たったものが確定）:
  1. duplicate            → 記帳しない。監査タブのみ（AD-1）
  2. entry_count > 0      → 必ず記帳（族シグナルは _audit_signal に落とすだけ）
  3. has_detail_rows      → 除外させない。赤い認識不能占位行
  4. family が非記帳族     → cc_summary は **MF タブへ金額 0 の提示行**（裁定 8）
                            points_only / info_notice は監査タブ
  5. それ以外              → 赤い認識不能占位行
```

> **2026-08-14 訂正**: 優先序 4 は当初「非記帳族はすべて監査タブ」と書いていたが、
> これは裁定 8（合計表のみの頁は MF タブへ金額 0 の提示行。顧客が「合計表を
> 上げたのに何も出てこない」状態にならないようにする）より前の記述だった。
> 裁定 8 が後であり趙の拍板なので、`cc_summary` の落とし先を MF タブへ訂正する。
> 実装は `page_family.resolve_page_disposition` の 1 箇所（`EXCLUDE_DEST_MF_TAB`）。

どのモジュールもこの関数を経由せずに頁の去向を決めてはならない。

> **移行の完了条件（2026-08-14 追記）**: T2 時点でこの関数は
> `page_family.resolve_page_disposition` に**存在するだけ**で、本番経路からは
> 1 箇所も呼ばれていない。`ocr_engine._yield_page_results`（1943-1996）が今も
> 独立に頁の去向を決めており、**システム全体としては単一裁決点になっていない**。
> 当初の T3〜T6 の DoD はどれもこの移行を要求していなかったため、放置すると
> AD-0 の不変式が黙って永久に着地しない。よって **T9 の DoD に移行完了を明記する**
> （下記）。この追記が無いと「モジュールは書いたが誰も使っていない」状態が
> 完成扱いになる。

### AD-1. 重複検出は D3 に一本化し、**書込前ゲート**として働かせる

**問題**: D2（元帳）と D3（指紋）が別々に重複判定を持っていた。D2 側は
`(issuer, 会員番号下5桁, 頁番号)` のキー単独依存で内容フィンガープリントが無い。

**裁決**:
- 重複判定は `page_dedup.py`（D3）の**二重署名 AND 規則**（識別キー一致 **かつ**
  内容ダイジェスト一致）に一本化する。片方だけの一致では絶対に除外しない。
- 判定は `_yield_page_results` を呼ぶ**前**に行う。重複頁は `_excluded_page` として
  yield され、`append_entries` に到達しない（＝MF に 1 行も書かれない）。
- D2 の元帳は自前判定を持たず、重複頁を累計に足さないだけ。
- 指紋生成に失敗したら **fail-open**（＝重複ではないとみなして記帳する）。

**根拠**: 単一署名での除外は偽陽性で仕訳を消す。F-2 のアメックス p1≡p3 は
明細も合計も完全一致するため指紋だけで捕まる。キー単独では
UC `4542-…-2***` / JCB `3541-…-2XXX` の**末尾マスク**（事実台帳 §3）で
下4桁キーが成立せず、別カードの同一視すら起こる。

### AD-2. 族分類は「事後説明器」。前置拒否権を持たせない

**問題**: D4 が `raw_data["page_kind"]` を読んで `point_info` / `information` /
`statement_summary` を直ちに `_excluded_page` にする案を出した。これは IP-401 で
`_is_envelope_page` が降格された経緯（CLAUDE.md）を正面から破る。

**裁決**: AD-0 の優先序に従う。`entries > 0` の頁を族シグナルが否決することはできない。
**ただし優先序 1 の duplicate は entries の有無より先に適用される**（AD-1）。
`page_kind` は分類器への**入力シグナルの一つ**に降格し、単独で頁を落とせない。

**根拠**: F-6 / F-10 の UC p2 が実在の反例 —— 「永久不滅ポイント」区画と明細12行が
同居する。ポイント語で頁を否決する設計だと 12 件が丸ごと消える。
順序ではなく**制御フローの形**で不可能にする。

### AD-3. `_apply_ocr_overrides` を新 doc_type で無効化する

**裁決**: `_OCR_OVERRIDE_EXEMPT_DOC_TYPES = {CREDIT_CARD, TRANSIT_IC}`。

**根拠**（2点、どちらも単独で十分）:
- **日付**: `_extract_date_from_ocr` の `_skip_keywords` に「カード」「ポイント」が含まれ、
  カード明細では全日付が fallback へ落ちて「最後に出た日付」が採用される。
  それが全行の B列 取引日を上書きする。逐行記帳では行ごとの利用日が正。
- **T番号**: F-11 のとおり券面のT番号は**カード会社自身**のもの。F-14 により
  カード明細は請求書等に該当せず、行ごとの加盟店登録番号は存在しない。
  `ocr_engine.py:1003` はキーが無くても代入するため、プロンプト側の改名では防げない。

### AD-4. 明細行の区画（section）は Gemini に出力させる

**問題**: D2 の `TOTAL_LABEL_SECTION` は**合計ラベル**でシードされており、
明細行がどちらの区画に属するかを決める手段が設計に無かった。

**裁決**: プロンプトが `sections[]`（区画の index / label / kind / subtotal）と
各行の `sec`（所属区画 index）を出力する。元帳はそれを消費する。
Python 側は `kind == "carry_over"` の行だけ `payment_summary` へ強制上書きする
（プロンプトの自己申告を最終的に信用しない保険）。

**根拠**: F-5 のアメックス カードB は「お支払い金額内容」区画（前回分口座振替 −35,808）と
「今月ご利用額」区画が縦に並び、それぞれ別の小計を持つ。区画を混ぜると検算が壊れる。

### AD-5. 記帳集合と検算集合を別軸で持つ（2026-08-14 改訂）

**裁決**: 行に 2 つの独立した属性を持たせる。

| 軸 | 値 | 用途 |
|---|---|---|
| `kind` | `expense` / `fee` / `credit_adjust` / `carry_over` / `charge` | どう記帳するか |
| `sec` | 区画 index | どの小計と突合するか |

**負数行の扱い（当初案を改訂）**:

| kind | 実例（F-5） | 会計上の性質 | 処理 |
|---|---|---|---|
| `credit_adjust` | ENEOS ポイントキャッシュバック −3,000 | 当月利用額の減額・返還 | **カード未払金を直接減らす**<br>借方 `未払金`（補助＝カード名）対象外 ／ 貸方 `雑収入` 対象外、**金額は abs(amount)**。当月利用額の検算にも入れる |
| `carry_over` | アメックス 前回分口座振替金額 −35,808 | 前月未払金の清償 | **記帳しない**。検算/監査のみ。銀行明細側で `借方 未払金 ／ 貸方 普通預金` として起票されるため、カード明細側でも起こすと二重計上になる |
| `charge` | nimoca 入金 現金 5,000 | SF残高へのチャージ | 記帳しない（裁定 2 の TBD-2 既定） |

**検算**: ENEOS の場合、通常利用で `貸方 未払金 18,503` が積み上がった後、
ポイント充当で `借方 未払金 3,000` が立つ。カード補助元帳の増加額は
**15,503** となり、券面の請求額と一致する（F-4）。

### 二度の設計変更の記録（同じ誤りを繰り返さないため）

| 版 | 案 | なぜ棄却したか |
|---|---|---|
| 当初 | 負数行は一律記帳しない | 未払金が 18,503 で増え、実請求 15,503 と食い違う。設計線 D4 の検証が P0（D4-b）として指摘 |
| 第2版 | 借方 `クレカ相殺` ／ 貸方 `未払金` | **向きが逆**。これでは未払金が 21,503 に増え、目的（請求額に合わせる）を達成できない。さらに MF 全 112 社の実測で、この科目は **7 社（約7%）にしか存在せず**、しかも**貸借対照表側＝仮払金的な一時科目**であって、ポイント処理用の科目ではないことが判明した（附録 D） |
| **現行** | 借方 `未払金` ／ 貸方 `雑収入` | 未払金が正しく減る。`雑収入` は抽査 14/14 社に存在する MF 標準科目（附録 D） |

**科目名は設定可能にする**: `config.CREDIT_ADJUST_CREDIT_ACCOUNT`（既定 `"雑収入"`）。
会社ごとの慣行差は実測で確認済みなので、ハードコードしない。

**根拠**: F-4 の ENEOS 実測 `7,380 + 11,123 − 3,000 = 15,503` は
負数行を含めて初めて一致する。F-5 が両者を明示的に別物として記録している。

### AD-6. 逐行記帳を Sheets 層で表現する（地基改造）

**問題**: `sheets_output.append_entries` は「1 文書 = 1 取引」設計。

```
sheets_output.py:113  _get_next_txn_no はキャッシュ命中で即返す
sheets_output.py:237  transaction_no = self._get_next_txn_no(...)   1 回の呼出で 1 番号
sheets_output.py:262  全 row が同じ transaction_no
sheets_output.py:263  取引日 = entries_data["date"]                 文書級
sheets_output.py:266  借方取引先 = vendor_name                      文書級
sheets_output.py:296  detect_anomalies が文書級 date/vendor/invoice を見る
sheets_output.py:396  self._tab_next_txn[tab_name] = actual_txn_no + 1
```

領収書ではこれが**正しい**（1枚のレシート = 1取引、複数品目 = 複合仕訳）。
MF の A列も「単一/複合仕訳の区別に使用」（F-12）がその語義。
だがクレカ明細の 100 行 ETC は**100 件の独立取引**であって複合仕訳ではない。

**裁決**: doc 級構造を壊さず、**明示ゲートで新旧経路を分ける**。

```python
line_mode = bool(entries_data.get("line_mode"))   # builder が立てる。既存は必ず False
```

| 列 | 旧経路（`line_mode=False`） | 新経路（`line_mode=True`） |
|---|---|---|
| A 取引No | 呼出ごとに 1 つ | **行ごとに連番** |
| B 取引日 | `entries_data["date"]` | `entry["date"]`（無ければ doc 級へ回帰） |
| F 借方取引先 | `vendor_name` | `entry["debit_vendor"]` |
| T 仕訳メモ | 文書級 `memo` | `entry["memo"]` |
| H 借方インボイス | `_sanitize_invoice_num(...)` | `_resolve_invoice_cell(...)`（AD-8） |
| 異常検知 | 文書級 parent | 行級 + `_suppress_invoice_flags` |

**取引No キャッシュの修正（Codex P0 指摘・実在バグ）**:
`line_mode` では 1 回の append で N 個消費するため、書戻しは
`self._tab_next_txn[tab_name] = actual_txn_no + len(rows)` でなければならない。
現行の `+ 1` のままだと、同一タブへの 2 回目の append が 2 番から始まり
**取引No が重複する**。復旧経路（`_with_tab_recovery`）でも N 連番を一括再割当てする。

「既存 doc_type 不変」は宣言ではなく**明示ゲート ＋ golden row snapshot テスト**
（A:AB 全 28 列を逐欄比較）で証明する。既存テストが無修正で緑なだけでは不十分
（Codex 指摘: テスト済みケースが壊れていないことしか示さない）。

### AD-7. 検算不一致の赤系マークは「監査行」に付ける

**問題**: 不一致カードの全行を遡及標色すると ETC 300 行が全部赤くなり、
赤の信号価値が消える。

**裁決**: 不一致は**カード単位で監査タブに 1 行**記録し、その行を赤系にする。
明細行は標色しない。

**実装接点（Codex P1 指摘・現状は接点なし）**:
`sheets_output.py:576 append_audit_row` は 7 列を append するだけで
severity も書式設定も持たない。`append_reconciliation_row(severity=...)` を新設し、
`_apply_anomaly_highlight` と同じ書式経路を通す。監査タブのスキーマ（7 列）は変えない
（`_` 始まりタブ名の GAS 削除規則と、既存の監査行との互換のため）。

→ **粒度そのものは TBD-5 として趙の裁定を仰ぐ**（技術判断で勝手に決めない）。

### AD-8. H列は事務所慣例に従い「空欄」。判定木は作らない（2026-08-14 全面改訂）

**当初案は破棄した。** MF 本番の実測（附録 C）により、当初の
「判定木を作り、特例に命中しない行は `控除なし` に倒す」設計は
**井戸会計事務所の実帳と正面から食い違う**ことが判明したため。

**実測事実**: 貸方＝未払金 の 133 件中 **111 件が「適格」** に該当し、
かつ画面上の H列は**空欄**（F-12 のとおり MF は空欄を「適格」と解釈する）。
金額の大半は 621〜3,300 円で、1 万円を超える行（140,002 / 77,000 / 24,771 等）は
公共料金や店舗購入であり、**適格請求書は別途保存されている**とみられる。
つまりこの運用では**カード明細は記帳のトリガであって控除の証憑ではない**。

**裁決（趙 2026-08-14）**:

1. **H列は空欄**（事務所慣例をそのまま踏襲）。
2. ただし **`amount >= 10000` の行に U列タグ `1万円以上: インボイス確認`** を付け、
   人が適格請求書の有無を確認できるようにする。
   閾値は「税込1万円**未満**」が少額特例の要件なので **`>=` で判定する**（`>` ではない）。
3. **コード上に「少額特例により適格」と書かない。** 少額特例には
   「基準期間の課税売上高 1 億円以下等」の事業者要件があり、プログラムには判定不能。
   空欄にするのはあくまで**事務所慣例の踏襲**であって、税法判断の自動化ではない。

**実装**: `config.INVOICE_COL_RENDERING` は残す（将来 TBD が動いたときの単一切替点）が、
credit_card / transit_ic の既定レンダリングは**空文字**とする。
`INVOICE_COL_VALUES` による import 時検証も残す（誤って不正な文字列が入るのを防ぐため。
空文字は明示的に許可値に含める）。

**留保**: 少額特例の判定単位は「一回の取引の税込金額」であり、
同一加盟店・同日の分割行、税抜/税込の OCR 誤抽、分割払い手数料などで
1 行 = 1 取引が崩れる場合がある（Codex 指摘）。タグは**注意喚起**であって
判定の保証ではない。この限界を摘要やメモに書かない（誤解を招くため）。

### AD-9. 書込前ゲートと書込後検算を分離する

**問題**（Codex P0）: `main.process_file` は逐頁で即 `append_entries` する。
EOF でしか判らない事柄で「記帳するか否か」を決めることはできない。

**裁決**: 判断を 2 層に分ける。

| 層 | 時点 | 決めること | 決めてはいけないこと |
|---|---|---|---|
| **書込前ゲート** | 各頁の `append_entries` 呼出前 | 重複頁か（AD-1）／行が記帳対象か（AD-5 の `kind`）／頁の去向（AD-0） | — |
| **書込後検算** | EOF（全頁処理後） | 検算結果の記録、監査行の追加、赤系マーク | **記帳の可否は決めない** |

検算が書込後になるのは趙の裁定 3（照常記帳 ＋ 赤系マーク）の当然の帰結であり、
設計上の妥協ではない。ただし**重複と非記帳行の判定は必ず書込前に完了していること**。

### AD-10. 外貨取引は円換算額のみを記帳する

**根拠**: F-9 の JCB は円貨・現地通貨額・換算レートの 3 つを併記する
（例: `9,238 円` / `57.60 USD` / `160.384 円/USD`）。

**裁決**: プロンプトのスキーマを `jpy_amount` / `foreign_amount` / `currency` / `fx_rate`
の 4 フィールドに分離する。MF の金額列には **`jpy_amount` のみ**を使う。
現地通貨額とレートは摘要へ回す。`jpy_amount` が取れず `foreign_amount` だけの行は
記帳せず赤い占位行にする（USD の数値を円として記帳する事故を構造的に防ぐ）。

### AD-11. 事務所慣例は doc_type 局部で踏襲する（グローバルを変えない）

MF 本番の実測（附録 C）で判明した井戸会計事務所の記帳習慣を採り入れる。
ただし**適用範囲は credit_card / transit_ic の出力層に限る**。

| 慣例 | 踏襲 | 適用範囲 |
|---|---|---|
| H列（借方インボイス）＝空欄 | する（AD-8） | 新 doc_type のみ |
| 貸方「未払金」の**補助科目＝カード名** | する | 新 doc_type のみ |
| 借方税区分は**省略名**『課仕 10%』 | する | 新 doc_type の**出力層のみ**。内部は canonical code を保つ |
| 負数行に『クレカ相殺』科目 | する（AD-5。ただし ポイント充当 のみ） | 新 doc_type のみ |

**貸方補助科目**: `sheets_output._determine_credit_sub_account`（711 行）は
既に doc_type で分岐している（receipt→社長名、purchase_invoice→取引先名）。
`CREDIT_CARD → カード名` を足すのは同じ設計の延長であって一貫性を壊さない。
貸方債務の相手は加盟店ではなく**カード会社**だからである。
既存 2 分岐は 1 文字も変更しない。

**税区分の省略名**: `receipt_aggregation.determine_tax_types()`（160 行）は
正式名『課対仕入10%』を返し、既存の fixture と摘要ロジックがそれに依存している。
**グローバルには変えない。** credit_card builder / MF レンダリング層でのみ
省略名に変換する。`anomaly_detector.detect_outlier_exempt_rows`（220 行）は
`== "対象外"` の精確等値しか見ておらず課税ラベルの表記には依存しないことを確認済み
（Codex がコードを読んで検証）。

## 附録 D: 勘定科目の全社実測（2026-08-14）

「クレカ相殺」を既定科目にしてよいかを判断するため、趙の指示で
**井戸会計事務所の全 112 社**の勘定科目を実測した。閲覧のみ。

### 調査方法（再現可能な形で記録する）

MF の事業者切替は「切替」リンククリック時に **JavaScript confirm ダイアログ**を出す。
これがブラウザを完全にブロックするため、fetch や URL 直叩き（`/user_status?cti=…&tid=…`）は
すべて 404 になる。`window.confirm = () => true` を注入してから click すると通る。
CLI（agent-browser）でループ化し、各社ごとに **要求した会社名と実際に読めた事業者名を突合**
してから記録した（この検証がなければ「全社が同じ結果」という偽の結論を書くところだった）。

### 結果 ①: 貸借対照表側（112 社全数）

| 状態 | 社数 | 会社 |
|---|---|---|
| 「クレカ相殺」有効 | **7** | 日本セノリティクス / 東利 / **資豊舎** / RQS / サトマート / ラクサ / Carエナジー |
| 「（×）クレカ相殺」＝無効化済み | 1 | **光栄電気商会** |
| 別名称の類似科目 | 3 | ENITY「クレカ相殺（×）」/ HLナレッジ「クレカ　アナザーレーン」「クレカ　JCB」（カード別に分けている）/ ソルナリアルティ「代表者クレカ」 |
| 該当なし | 90 | — |
| 事業者名の取得のみ失敗（科目リストは取得済み） | 11 | 判定は有効だが「検証済み」とは扱わない |

**訓練サンプルの 2 社が正反対**という事実が決定的だった:
`資豊舎`（JCB サンプルの宛先）は有効、`光栄電気商会`（TS CUBIC / ENEOS の宛先）は無効化済み。
同じ 1 バッチのサンプル内で一方は使えて一方は使えない。

### 結果 ②: 損益計算書側（14 社抽査）

| 科目 | 存在した社数 |
|---|---|
| `雑収入` | **14 / 14** |
| `売上値引・返品` | 14 / 14 |

`仕入値引・返品` も全社にあるが採用しなかった。カード明細の中身は
通信費・水道光熱費・旅費交通費などの経費が大半で仕入ではないため、
仕入項目に混ぜると PL が汚れる。

### この調査の既知の限界（誇張しないために明記する）

結果 ① は **貸借対照表側のみ**を読んでいる。MF の勘定科目画面は
`/bs_items`（既定）と `/pl_items` にタブが分かれており、当初 `/items` だけを
読んでいたため PL 側が抜けていた。したがって「クレカ相殺を PL 側に作っている会社」が
あれば ① は取りこぼす。ただし結論（＝この科目を既定にしない）は
「7 社しかない」「向きが目的と逆」「BS 側＝一時科目の性質」の 3 点で支えられており、
取りこぼしがあっても変わらない。
