1. **B-F1 ＋ B-F2 ＋ B-F3 → 錨をファイル内で引き継げば TS CUBIC p6 の 57 行が直る。**
   これが 66 件の大半を占める。
2. **B-F5 → 行級の OCR 日付補助は実装しても効かない。** 列順が崩れている頁で
   行と日付を対応づける手段が無い。「頁に 1 個だけ日付がある頁に限り全行へ貼る」
   という限定形も、TS CUBIC p6 には 4 種類以上の日付が在るので発火しない。
3. **B-F6 → ENEOS p2 も同じ形。** 錨さえ在れば 3 行中 2 行が直る。残る 1 行は
   キャッシュバック行で `month_day` が空、**正しい終態は「空欄＋赤い異常タグ」**。
4. **B-F9 → 「日付が全行空の頁を 1 回だけ再呼出」は不要。** 3 回とも逐字同一で、
   失敗の形は「Gemini が何も返さない」ではなく「`month_day` を返しているのに
   プログラムが錨を持たず使えない」だった。再呼出は費用と非決定性を増やすだけ。
   なお現行 prompt は【最重要】で「作成日も読めないときだけ date を null にし、
   month_day に券面の逐語を残してください」と指示しており、**Gemini は指示どおりに
   動いている**。欠けているのは受け取る側の半分である。

> **趙への報告事項**: 指令にあった「行級 OCR 日付補助」は、実測した券面 2 種では
> **作っても効かない**。OCR テキスト側は列順が崩れて行と対応づけられず（B-F5）、
> Gemini 側は既に `month_day` を正しく返している（B-F1 / B-F6）。
> つまり**カード経路で欠けていたのは OCR ではなく、錨を頁跨ぎで持ち回す仕組み**
> だった。AI＋OCR を組ませた目的（識別漏れの相互補完）は、日付については
> 「Gemini が月日、プログラムが年」という分担で既に達成されており、
> その分担が p2 以降で成立していなかったのが 66 件の正体である。

## 2. 目標と非目標

### 目標

1. **G1**: 重複頁が記帳されない（`CREDIT_CARD_DEDUP_MODE=exclude` の既定で）。
2. **G2**: 重複と断定できないが疑わしい頁（近似一致）が監査タブで可視になる。
3. **G3**: 明細書作成日をファイル内で引き継ぎ、`month_day` しか無い行の年を確定する。
4. **G4**: 上記いずれも **記帳を止めない**（IP-401）。頁は必ず 1 行以上 yield する。

### 非目標（やらない。理由を明記する）

- **行級の OCR 日付補助** — B-F5 により列順が崩れて行と日付を対応づけられず、
  B-F6 のとおり Gemini 側は `month_day` を返せている。作っても効かない。
- **日付が全行空の頁の再呼出** — B-F9（3 回とも逐字同一）により不要。
- **錨の OCR 補助**（当初案 G4）— **B-F10 により現時点で必要が無い。**
  Gemini は錨の在る頁で錨を返せている。錨を落とす頁が実測されたら再検討する。
  仮に錨がファイル全体で取れなくても、症状は「全行の日付が空 ＋ 赤い
  `missing_date` タグ」であって**無音ではない**（`anomaly_detector.py:107` severity=high）。
- **`month_day='330'` のような区切り無し表記の解釈** — B-F11 のとおり 3 回に 1 回
  起きるが、`'112'` が 1/12 とも 11/2 とも読める真の曖昧性がある。1 行救うために
  誤年の危険を作らない（趙の既裁定「空欄より無音の誤年の方が危険」）。
- **T9 / T8c** — 別 Plan。
- **`page_family.py` の分割**（755 行 / 上限 800）— 本 Plan は同ファイルに
  数行しか足さない。分割は T9 で行う。

## 3. A 章 — 重複頁の接線

### 3.1 判定は既に在る。足りないのは 3 本の線

```
[現状]  safe_fingerprint  ──✕ 誰も呼ばない
        PageDedupIndex    ──✕ 誰も作らない
        resolve_page_disposition(None, …)   ← ハードコード

[目標]  process_pipeline が 1 ファイル 1 個の索引を作る
          └→ _yield_page_results が 頁ごとに 指紋 → classify
               └→ _resolve_card_disposition が verdict を裁決者へ渡す
               └→ 記帳できた頁だけ remember
```

### 3.2 状態の置き場所 — 新モジュール `card_file_state.py`

頁跨ぎの状態は 2 種類になる（A 章の重複索引、B 章の錨）。両方を
`_yield_page_results` の引数へ個別に足すと署名が膨れ、AST 番人も 2 本要る。
**1 ファイル分の状態を 1 個のオブジェクトに畳む。**

置き場所を `ocr_engine.py` にしない理由: 既に 2916 行で上限 800 を大幅超過
（CLAUDE.md / 母 Plan §4）。新モジュールは stdlib のみに依存させ、venv 無しで
単体テストできる状態を保つ（`page_family` / `card_prompts` と同じ方針）。

```python
# card_file_state.py（新規・約 120 行）
class CardFileState:
    """1 ファイル（= 1 回の process_pipeline 呼出）分の頁跨ぎ状態。

    **明細行は 1 行も保持しない**（逐頁ジェネレータのメモリモデル厳守）。
    持つのは頁あたり数百バイトの指紋要約と、券面の錨 1 個だけ。
    """
    __slots__ = ("dedup", "_anchor")
```

責務:

| メソッド | 役割 |
|---|---|
| `classify(doc_type, page_num, ocr_text, raw_data)` | 指紋を作って `(verdict, token)` を返す。card 系以外は `(None, None)` |
| `remember(token, page_num)` | その頁を索引へ登録する。`token` が `None` なら何もしない |
| `absorb_anchor(doc_type, raw_data, ocr_text, page_num)` | この頁で錨 run を開く／閉じる（B 章 §4.1） |
| `apply_anchor(doc_type, raw_data, ocr_text)` | 錨の無い頁の `card.statement_date` を補う。継承したら `True` を返す（B 章） |

`token` は `ocr_engine` からは**中身を見ない不透明な物体**として扱う
（実体は `PageFingerprint`）。内部に「直前の指紋」を退避して
`remember(page_num)` にする案もあったが、classify と remember の間で頁が
入れ替わる事故を型で防げない。**そもそも取り違えられない形**にする
（Codex 評審 C8）。

**全公開メソッドは例外を外へ出さない**（Codex 評審 C10）。失敗したら
その機能だけ無効化して記帳を続ける —— `page_dedup.safe_fingerprint` と
同じ契約で、`CardFileState` が落ちて頁が消えることを構造的に禁じる。

### 3.3 接線の位置

`_yield_page_results` の非領収書枝、`_build_doc_result` の**後**・
除外判定の**前**（＝ T8 が P-B と呼ぶ位置。逐頁ループと尾段の両方が通る）。

新引数は `page_class` と**同じ形**にする ——
`_yield_page_results(..., page_class=None, state=None, page_num=None)`。
既定値を持たせるのは、既定値を禁じると 9 ファイル 40 箇所のテスト呼出が
一斉に赤くなり、本質と無関係な改修で目が曇るため。**生産の呼出点が
渡していることは AST 番人テストが縛る**（既存 `BothCallSitesPassPageClassTest`
を拡張。`page_class` で既に確立した前例）。`state is None` のときは
その場で使い捨ての `CardFileState()` を作る（＝頁跨ぎの効果は無いが
None 分岐を関数中に散らさない）。

```python
verdict, token = state.classify(doc_type, page_num, ocr_text, raw_data)
disposition = _resolve_card_disposition(
    doc_type, page_class, result, raw_data, prefix, verdict)
if disposition is not None and disposition.action == ACTION_EXCLUDE:
    yield _blank_result(...)              # 既存のまま
    return
if result.get("entries"):
    state.remember(token, page_num)       # **記帳できた頁だけ**登録する
```

`remember` を「entries が空でない頁だけ」にする理由（Codex 評審 C3 で
根拠を訂正）: `sheets_output._should_write_row` は `line_mode` のとき
`amount is not None` を返すので、**金額 0 の占位行も書かれる**
（`sheets_output.py:95-98`）。したがって「金額 0 は skip される」という
当初の根拠は誤りだった。

正しい根拠は別にある —— **`_unrecognized` に終わった頁（builder が 1 行も
組めなかった頁）を索引に入れない**ため。その頁は Sheets に赤い占位行しか
残さないのに、指紋は `raw_data["rows"]` から作られるので
`is_eligible()` を満たしうる。登録してしまうと、後続の真の重複頁が
除外され、**その明細はどこにも 1 回も記帳されない**。

### 3.4 重複除外は「行欠けの疑い」より先に効く（A-D1）

`_resolve_card_disposition` は現在、除外裁決が出ても
`card_salvage.page_marks` が行欠けを疑えば `None` を返して除外を取り消す。

**重複頁ではこの取り消しを行わない。** 理由:

`DUPLICATE` に到達する条件は「識別キー一致 **かつ** 内容ダイジェスト一致」で、
ダイジェストは (日付, 金額) の並びと頁合計から作る。つまり DUPLICATE の頁は
**原本の頁と (日付, 金額) が逐字一致している**。原本側で行が欠けていたなら
同じ欠けが原本の監査行に既に記録されている。重複側を除外しても新たに失う
情報は無く、除外しなければ確実に二重計上になる。

実装: `Disposition` に `is_duplicate: bool = False` を足し、
`resolve_page_disposition` が重複と断じたときだけ True にする。
`_resolve_card_disposition` はこのフラグで分岐する。
**理由文字列の前方一致で判定しない**（reason が増えるたび main 側の分岐を
書き足し忘れる、という T8 で既に踏んだ形を避ける）。

### 3.5 近似一致は「除外しないが黙らない」（A-D2）

`page_dedup` は DUPLICATE 以外に 2 つの近似判定を返すが、現状どちらも
何も起こさない。Gemini の非決定性で 1 行でも日付がぶれると DUPLICATE が
KEY_CONFLICT へ落ちるため、**接線しただけでは「重複を見逃したこと」が
誰にも見えない**。

| verdict | 意味 | 本 Plan での扱い |
|---|---|---|
| `duplicate` | キー一致 ∧ 内容一致 | 除外（既定）。監査タブへ |
| `key_conflict` | キー一致 ∧ 内容不一致 | **記帳する**。監査タブに注記 |
| `content_only` | 内容一致 ∧ キー不完全 | **記帳する**。監査タブに注記 |
| `unique` / `not_eligible` | — | 何もしない |

これは検出であって処分ではない。`resolve_page_disposition` の優先序 2
（entries があれば必ず記帳）は 1 バイトも変えない。

### 3.6 監査タブの日本語（A-D3）

`0588bdc` で日本語化した約束を守るため、新しい reason キーは同時に
`sheets_output._AUDIT_REASON_JA_PARAM` へ登録する。

`page_dedup._detail` は現在 `key=…;amt=…` を `;` で連結しており、
`audit_reason_ja` の分割規約（`;` 区切り・`:` でキーと引数）と噛み合わない。
**`_detail` の書式を `キー:引数` へ揃える**（`test_page_dedup` は `_detail` の
書式を断言していないので固定は壊れない）。

| reason（機械語） | 監査タブの表示 |
|---|---|
| `duplicate_page:orig=p1` | 1 ページ目と同じ内容のため記帳していません |
| `dup_amount:17295` | 重複と判定した金額は 17,295 円です |
| `dup_key:AMEX/…/1/6` | 照合キー: AMEX/…/1/6 |
| `dup_key_conflict:orig=p1` | 1 ページ目と同じカード・同じページ番号ですが内容が違います（原票をご確認ください） |
| `dup_content_only:orig=p1` | 1 ページ目と明細の中身が一致します（重複の疑い。原票をご確認ください） |

### 3.7 メモリ（逐頁モデルを壊さないこと）

1 頁あたり `PageFingerprint`（5 スカラ ＋ sha256 の 64 文字）＋ dict 2 本の
エントリ。実測見積で 300〜400 バイト/頁。100 頁 PDF で 40KB 未満。
**明細行・画像・OCR 生テキストは 1 バイトも保持しない**（`build_content_digest`
は digest を返した時点で行を捨てる）。

## 4. B 章 — 日付の錨をファイル内で確定する

### 4.1 B1 — 錨のファイル内引き継ぎ

**問題**（B-F1〜B-F3）: 明細書作成日はアメックスなら全頁の頁頭に在るが、
TS CUBIC / ENEOS は p1 だけ。逐頁処理なので p2 以降は錨を持てず、
`_card_date` の年確定が原理的に効かない。

**方式**: `CardFileState` が「そのファイルで最後に読めた錨」を保持し、
錨を持たない頁の `raw_data["card"]["statement_date"]` を補う。

**接線の位置**: `_yield_page_results` の中で、`ENTRY_BUILDERS` の builder を
呼ぶ**前**（`_build_doc_result` の前）。builder（`card_entries._build`）が
`card.statement_date` を読むので、それより後では効かない。順序は
`absorb_anchor` → `apply_anchor` の 2 段（自前の錨を先に採ってから補填する
ので、自前の錨を持つ頁が他頁の錨で上書きされることはない）。

**これは推測ではない**: 補う値は**同一 PDF 内の券面に印字されている**
明細書作成日である。prompt の「跨頁禁止」は Gemini に対する制約
（他頁の**明細行**を捏造させない）であって、プログラムが同一ファイル内の
券面記載を使うことを禁じてはいない。

**別明細書の混在は実在する**（B-D1。Codex CRITICAL を実測で確認）:
`card_prompts` 自身が「1 つの PDF に別会社・別明細書のカード明細が混在する
ことがあります」と書いており、**実測でも起きていた** —— TS CUBIC の PDF は
p1 が トヨタファイナンスの合計表（1 頁完結）、p5〜p9 が別建ての ETC 副明細書
（5 頁）である（B-F14）。錨が明細書の境界を越えると**無音の誤年**になり、
趙の既裁定「空欄より無音の誤年の方が危険」に反する。

**同一性の判定には券面の頁付け（`statement_page`）だけを使う。** 実測で
他の候補は 2 つとも棄却された:

| 候補 | 棄却の理由（実測） |
|---|---|
| `issuer` | TS CUBIC p5 = `トヨタファイナンス株式会社` / p6 = `NEXCO`。**同一副明細書内で食い違う**（B-F15） |
| `member_no` | ENEOS p1 = `…8602` / p2 = `…3726`。**同一明細書内の副カードで食い違う**（B-F16） |
| **`statement_page`** | TS CUBIC p5=`1/ 5ページ` → p6=`2/5`、ENEOS p1=`1/2ページ` → p2=`2/ 2ページ`。**3 例すべてで一致**（B-F17） |

```
錨 run = (statement_date, total_pages, expected_next_page)

開く: 頁が自前の statement_date を持ち、statement_page が (1, N) と読める
      → 新しい run を開く。**既存の run は必ず閉じる**。expected_next_page = 2
      （N == 1 ならその場で閉じる。1 頁完結の合計表から誰も継承しない）

継承: run が開いている ∧ 頁が自前の statement_date を持たない
      ∧ statement_page が (k, N) と読める ∧ N == run.total_pages
      ∧ **k == run.expected_next_page**（飛びを許さない）
      ∧ OCR テキストに頁付けが在る場合はそれと矛盾しない
      → 継承する。expected_next_page = k + 1。k == N で run を閉じる

閉じる: 上のどれにも当てはまらない頁を見たら run を閉じる（fail-closed）。
      特に **自前の錨を持たない (1, N) 頁**を見たら閉じる ——
      そこから新しい明細書が始まっている徴候だから。
```

**なぜ「最後に読めた錨」ではなく run なのか**（Codex 評審 R2-1 / R2-2）:
単に「最後の錨を使う」だと次の 2 つの反例が通る。

| 反例 | 旧規則 | run 規則 |
|---|---|---|
| A `1/2`(錨) → A `2/2` → B `1/2`(錨読取失敗) → B `2/2` | B p2 が A の錨を継承 | B の `1/2` を見た時点で run が閉じる → 継承しない |
| A `1/5`(錨) → A `2/5` → B `1/5`(錨あり) → A `3/5` | A p3 が B の錨を継承 | B が run を開き直すので expected=2。A p3 の k=3 は不一致 → 継承しない |

どちらも**空欄に倒れる**（誤年ではなく `missing_date` の赤タグ）。

**OCR は「必須の裏取り」ではなく「拒否権」として使う**（Codex 評審 R2-3 を一部採納）:
Codex は「Gemini の `statement_page` を単独で信頼せず、OCR と一致したときだけ
継承せよ」と建議した。**実測でこれは採れない** —— 直したい 2 頁
（TS CUBIC p6 の 57 行、ENEOS p2 の 2 行）は**どちらも OCR テキストに頁付けが
無い**（B-F18）。必須にすると 59 行すべてが空のまま残り、B 章が丸ごと
無意味になる。

そこで非対称にする: **OCR に頁付けが在って Gemini の値と食い違うときだけ
継承しない。OCR に頁付けが無いときは Gemini を使う。** 照合には
`page_dedup._normalize_page_label` と同じ正規化を使う（同じ券面を 2 通りの
規則で読まない）。

**残る穴を隠さない**: この非対称により、「Gemini が別明細書の頁付けを
**開いている run の次の頁番号ちょうど**に誤読し、かつ OCR にも頁付けが
無い」場合は誤年が入りうる。run 規則によって的は「任意の後続頁」から
「ちょうど次の 1 頁」へ狭まっているが、ゼロではない。§8 の R7 に載せ、
下の B-D3（監査タブへの記録）で可視にする。

**無音にしない**（B-D3。Codex CRITICAL の後段への対応）:
継承した錨を使ったファイルは、**ファイルにつき 1 回**監査タブに記録する。

    date_year_from_page:5/5   →  「このページには明細書作成日が印字されて
                                  いないため、5 ページ目（1/5 ページ）の
                                  作成日から年を決めました」

頁ごとではなくファイルにつき 1 回にするのは、TS CUBIC のように明細頁が
5 枚ある券面で毎頁鳴ると監査タブが狼少年になるため（`cc_summary` を
注記しないと決めたのと同じ理由）。

### 4.2 引き継ぎが「正しい年を壊さない」ことの論証（B-D2）

`_card_date` は Gemini が完全な日付を入れていても**年を上書きする**（T8b の裁定）。
したがって錨を持たなかった頁が錨を持つようになると、これまで素通りしていた
日付が書き換わる。壊さないことを示す。

`_nearest_past(m, d, ref)` は「(m, d) を持つ日付のうち `ref` を超えない最大のもの」
を返す。Gemini の日付 `g` が正しく、**かつ `g <= ref`** であれば、(m, d) =
(g.month, g.day) を持つ `ref` 以下の最大の日付は `g` 自身である —— 1 年前の
同月日は `g` より小さいので選ばれない。よって
**`g <= ref` が成り立つ範囲では、正しい日付は 1 件も変わらない**。

**前提を明記する（Codex 評審 C2 で指摘・採納）**: この論証は `g <= ref` に
依存しており、「明細書は作成日以前の利用しか載せない」という業務上の性質が
その根拠である。**しかしこれは定理ではなく経験則**で、`_card_date` の
docstring 自身が「利用日が作成日より後になる券面では前年へ倒れる」という
局限を既に宣言している（`card_entries.py:661`）。錨の継承はこの局限の
**適用範囲を広げる**（今まで錨が無く素通りしていた頁にも当たるようになる）。

したがって「常に安全」とは書かない。代わりに**測る**:
§9 の判定 7 として「改修前に日付が入っていた 289 行が逐字同一であること」を
受入基準に入れる。反例が出たら実物を添えて規則を見直す。

### 4.3 B 章が触らないもの

- `_apply_ocr_overrides` は 1 バイトも変えない（B-F8 の豁免は正当なまま）。
- `_ic_date`（transit_ic）は触らない。規則が違う（実行日基準・印字を尊重）。
- prompt は触らない。T8b-3 の回帰（禁止条項の作用域が広がって年が壊れた）を
  繰り返さない。**券面に錨が在るならプログラムで確定させる**（趙の教訓）。
